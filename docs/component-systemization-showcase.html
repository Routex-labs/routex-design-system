Routex Design System · UI systemization

Navigation 원본 화면을 Runtime Kit으로 옮기는 방법

원본 Flutter UI에서 반복되는 시각 결정은 디자인시스템 package가 소유하고, 화면의 도메인 데이터·상태·다음 동작은 소비 앱이 소유한다. 이 문서는 그 경계를 실제 코드 전후로 설명한다.

1. 한 줄 결론

package는 “어떻게 보이고 반응하는가”를 소유하고, 앱은 “무슨 데이터를 보여주며 누르면 무엇을 하는가”를 소유한다.

RoutexTravelModeBar는 색·간격·선택 상태·큰 글자 대응·접근성을 고정한다. 반면 어떤 이동수단이 실제로 가능한지, 선택 결과로 API를 호출할지, 길찾기 상태를 바꿀지는 Navigation 앱이 결정한다.

2. 모듈화와 패키지화는 다르다

이번 작업에서 모든 UI와 앱 로직을 package로 옮기는 것이 목표가 아니다. 재사용 경계가 필요한 시각 결정만 Runtime Kit으로 승격한다.

구분이 저장소의 예소유하는 것소유하지 않는 것
원본 앱 UINavigation/client/lib/widgets/현재 화면을 빨리 만들기 위한 조합과 앱 테마다른 앱이 재사용할 안정된 API
앱 모듈apps/showcase/lib/src/mockup/states/화면 상태, 도메인 값, 콜백, package 조합공통 padding·radius·typography의 반복 결정
Runtime Kit packagepackages/routex_design_system/semantic token, 컴포넌트 anatomy, 상태, semantics, 반응형 규칙Navigation 모델·API·MapLibre controller·Dijkstra
Showcaseapps/showcase/실제 공개 API를 조합해 상태와 화면을 검수package 컴포넌트의 사설 복제품

소비 앱은 package의 내부 파일을 import하지 않고 package:routex_design_system/routex_design_system.dart 하나만 import한다. 내부 token 수치가 바뀌어도 public API가 유지되면 앱 변경 범위를 줄일 수 있다.

4. 예시 1 — TravelModeBar를 RoutexTravelModeBar로 바꾸기

원본의 도메인 타입과 콜백은 앱에 남기고, 화면마다 반복되던 외형·선택 상태·큰 글자 대응을 package로 옮긴다.

현재 원본 앱 코드

class TravelModeBar extends StatelessWidget {
  final RoutePlanMode selected;
  final List<RoutePlanMode> modes;
  final ValueChanged<RoutePlanMode> onSelected;

  @override
  Widget build(BuildContext context) {
    if (modes.length < 2) return const SizedBox.shrink();

    return Material(

      borderRadius: BorderRadius.circular(14),
      child: Padding(

소비 앱 코드

도메인 값은 매핑하고, 시각 값은 넘기지 않는다

import 'package:routex_design_system/routex_design_system.dart';

final options = modes
    .map((mode) => RoutexTravelModeOption(
          id: mode.name,
          label: mode.label,
          icon: mode.icon,
        ))
    .toList(growable: false);

RoutexTravelModeBar(
  options: options,
  selectedId: selected.name,
  onSelected: (id) {
    final mode = modes.firstWhere((item) => item.name == id);
    onSelected(mode); // 앱 상태·API 흐름은 앱이 소유
  },
)
package 안으로 이동한 결정

Colors.white, 원시 fontSize: 13, BorderRadius.circular(10/14), 내부 padding, 선택색, 최소 높이, horizontal overflow와 semantics가 RoutexTravelModeBar 안으로 들어간다. 앱은 RoutePlanMode와 실제 가용 수단만 전달한다.

// packages/routex_design_system/lib/src/patterns/routex_travel_mode_bar.dart
class RoutexTravelModeBar extends StatelessWidget {
  const RoutexTravelModeBar({
    required this.options,
    required this.selectedId,
    required this.onSelected,
    super.key,
  });

  final List<RoutexTravelModeOption> options;
  final String? selectedId;
  final ValueChanged<String> onSelected;

  @override
  Widget build(BuildContext context) {
    if (options.length < 2) return const SizedBox.shrink();
    final itemWidth = _widthFor(MediaQuery.textScalerOf(context));
    return Semantics(
      container: true,
      label: '이동수단',
      child: SingleChildScrollView(
        scrollDirection: Axis.horizontal,
        child: _RoutexModeSurface(
          options: options,
          selectedId: selectedId,
          itemWidth: itemWidth,
          onSelected: onSelected,
        ),
      ),
    );
  }
}

위 코드는 실제 package 구현의 핵심만 뽑은 예시다. 내부에서는 RoutexColorTokens, RoutexSpacing, RoutexRadii, RoutexTypography, RoutexMetrics를 사용한다. 소비자가 padding·radius·font를 다시 주입할 수 없다는 점이 핵심이다.

6. 실제 적용 순서와 실패 조건

  1. 원본 UI를 분류한다. 반복되는 시각·상태·접근성 결정인지, 아니면 API·지도·화면 상태 같은 앱 책임인지 먼저 나눈다.
  2. 중립 API를 만든다. package에는 RoutePlanMode 대신 id/label/icon 같은 재사용 입력만 둔다.
  3. package 내부에서 token과 상태를 닫는다. 소비자가 padding, fontSize, radius로 외형을 다시 만들 수 없게 한다.
  4. Showcase에서 실제 package를 조합한다. Showcase 전용 복제품을 만들지 않고 360/390px, text scale 1.0/1.3/2.0과 상태를 확인한다.
  5. 제품 화면은 pilot으로 교체한다. 새 컴포넌트가 안정화되기 전에는 호환 wrapper를 두고, stable release tag를 고정한 뒤 원본을 제거한다.
실패 조건무슨 문제가 생기나막는 규칙
package가 RoutePlanMode·API·MapLibre를 import디자인 시스템이 Navigation 앱에 종속되어 다른 제품에서 재사용되지 않는다.package는 Flutter UI와 semantic input만 알고, 도메인·지도·API는 소비 앱에 둔다.
소비자가 padding·radius·TextStyle을 직접 전달같은 컴포넌트가 화면마다 다시 달라져 시스템화가 무너진다.외형 knob를 public API로 열지 않고 variant/state만 받는다.
Showcase가 package 컴포넌트를 복제전시 화면은 통과하지만 실제 package 품질은 검증되지 않는다.Showcase는 public barrel만 import하고 실제 컴포넌트를 렌더링한다.
하나뿐인 이동수단에도 선택 바를 표시선택할 수 없는 UI가 빈 자리를 차지하고 사용자를 혼란시킨다.RoutexTravelModeBar가 옵션 수를 검사해 숨긴다.
48dp 터치 영역·semantics·큰 글자 검증 누락기능은 되지만 실제 사용 환경에서 누르기 어렵거나 텍스트가 잘린다.package 테스트와 Showcase fixture에서 상태·폭·text scale을 함께 검증한다.
제품 앱이 package의 main이나 로컬 path를 release에서 사용어떤 코드가 배포됐는지 재현할 수 없고 변경이 갑자기 전파된다.release tag 또는 commit을 고정한다.
현재 저장소의 공급 경로

개발 중 Showcase는 ../../packages/routex_design_system path dependency로 실제 package를 바로 검수한다. 제품 앱에 넣을 때는 계획대로 v0.1.0 같은 release tag와 path: packages/routex_design_system을 고정한다. `main` branch나 개인 로컬 경로를 release에 직접 연결하지 않는다.
